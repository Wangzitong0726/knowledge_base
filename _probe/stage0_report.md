## 2.1 事故记录：last-token 取位错误（本阶段最重要的产出）

**症状**：长度分桶自检报 `逐行 cos = 0.042`，向量错位。而**这正是我做分桶自检的理由**——排序后还原下标若写错，块与向量会静默错配。

**排查**：先用假数据单独验置换逻辑 → 置换**完全正确**。于是嫌疑转向「向量本身在不同分批下变了」。逐条实测，规律立刻现形：

```
batch=2  → t1(16token,最长)=1.000  t3(97,最长)=1.000  t5(32,最长)=1.000
           其余 0.072 / 0.044 / 0.075 全错
batch=6  → 只有 t3(97 token,最长)=1.000，其余全错
```

**每个 batch 里只有最长的那一条是对的，被 pad 的全错。**

**根因**：`idx = attention_mask.sum(dim=1) - 1`。
这是**右 padding** 的公式。左 padding 的 mask 形如 `[0,0,…,1,1,1]`，
真实 token 在尾部，每行最后一个真实 token **恒等于最后一列**（`seq_len-1`），
与 pad 宽度无关；而 `sum-1` 给出的是 `L-1`，在被 pad 的行上落到序列**中间**。
只有「最长、没被 pad」的行上两者才相等——与观测规律完全吻合。

**为什么危险**：取中间 token 的隐状态**不是乱码**，是一个合法的、带语义的向量。
所以它不报错、不崩溃，检索还能出结果，只是所有被 pad 的块**全部降质**。
若不是分桶自检歪打正着，这个 bug 会一路带进索引里。

**修复**：改为找每行最后一个 `mask==1` 的位置：
```python
last = mask.size(1) - 1 - mask.flip(dims=[1]).long().argmax(dim=1)
```
这个写法对左/右 padding 都对，避免日后有人改了 `padding_side` 又静默出错。

**纪律教训**：这次拦住它的是「假设自己的代码可能错、并写了一关专门去证伪」，
而不是「测了、过了、收工」。**测试的强度必须覆盖到最容易错的那些输入**
（这里是「被 pad 的行」，而初版测试恰好避开了它）。

### 关 3 · 吞吐量 —— **这是个真问题**

**实测（800 字块 ≈ 508 token，batch=8）：**

| 字数 | token | 块/秒 | 有效 TFLOPS |
|---|---|---|---|
| 100 | 63 | 4.59 | 0.345 |
| 200 | 127 | 2.03 | 0.307 |
| 400 | 255 | 0.99 | 0.301 |
| 800 | 508 | **0.47** | 0.282 |
| 1600 | 1017 | 0.22 | 0.271 |

**读法一：块/秒 与 token 数严格成反比**（每加倍长度，速率正好减半）。
说明**耗时 ∝ 总 token 数**，而非块数。

> **这条直接改变建库策略：缩短块长不会省时间。**
> 800 字切 14000 块，与 400 字切 28000 块，总 token 相同、总耗时相同。
> 唯一能省时间的只有「少喂语料」或「换更快的运行时」。切块参数应纯粹按检索效果定，不必迁就算力。

**读法二：有效算力恒定在 ~0.3 TFLOPS**（16 线程 AVX2，峰值约 0.64 TFLOPS，利用率约 47%）。
利用率正常，**代码没有明显缺陷，是这台机器就到这个水平**。CPU 上约 250–290 token/秒。

## 3. dtype 与量化实测

| 方案 | 块/秒 | 相对 fp32 | 结论 |
|---|---|---|---|
| **fp32** | 0.48 | 1.00x | 采用 |
| bf16 | 0.08 | **0.17x（慢 6 倍）** | ❌ 弃 |
| int8 动态量化 | 0.63 | 1.32x | 提速有限，且给研究语料引入量化误差，不划算 |

> bf16 慢 6 倍印证了预判：这台 AMD CPU 无 BF16 硬件加速，回退到慢速模拟。
> 模型卡 native dtype 是 bfloat16，**照抄会踩坑**。

## 4. 对后续阶段的影响

- **全库耗时估算**：按 fp32、0.48 块/秒计，
  1.4 万块 ≈ **8.2 小时**；5 千块 ≈ 2.9 小时。
- 这是**一次性成本**，可挂夜间跑。但**每次改切块参数就要重跑**——所以切块方案要先定死再灌。
- **阶段 1（抓取）不受此问题阻塞**，可先推进。
- 若要压缩到 1 小时以内，需减少语料范围（见阶段 1 的语料取舍），
  或改走 llama.cpp / ONNX Runtime 路线（未实测，另行评估）。

## 5. 遗留

- 长度分桶（sort by length 再分批）可回收 padding 浪费，
  但按 800/120 顺序切块时块长方差小，收益有限——待阶段 3 实测块长分布后再定。
- 本机可用内存偏紧（本次实测期间约 5GB 可用），fp32 模型占约 2.4GB；
  大批量灌库时需注意，必要时减小 batch。
